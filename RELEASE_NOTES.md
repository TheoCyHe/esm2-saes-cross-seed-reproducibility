# RELEASE_NOTES.md — what release 1.0 contains
What this is for: what each part of the release contains; at which level each of the study's reported numbers can be recovered from it; which parts of the study the workshop paper leaves out; what the export changed in the files; where the reproduction and the tests have been run; and what was not done.
Who reads it: a reader of the released repository who wants more detail than `README.md` gives. The build that made the release wrote this file, from its own counts.
Current as of: 2026-11-18 (the release built from the working repository's commit `8f6a313`).

## 1. What each part contains

**Which of the three levels of reproduction each part supports.** `README.md` ("Reproducing the reported numbers") defines the levels: level 1 reruns the pipeline, level 2 recomputes the main numbers from the derived bundle, and level 3 is the provenance check.
- **The repository** holds the code of all three levels. Level 1 needs it with the path placeholders set, and also the activation cache and GPU time, which the release does not supply; the pipeline was not rerun from this export (§5).
- **The derived bundle** supports level 2: `scripts/reproduce_table1.py` recomputes the main numbers from it alone. §2 says, for each row of the study's reported numbers, whether the bundle recovers it and at which coverage level; the rows that script recomputes are the ones marked REGENERATED, and some rows are not recovered from the bundle at all.
- **The decoders** support one part of level 1 without retraining: decoder-space matching. No script here computes a match rate from the decoder files; `README.md` (level 1) says how they are used. The matching rule that requires the encoder matching and the decoder matching to agree needs the encoders, and alignment scores and activation-correlation matching need the activation cache and the encoders; neither is released.
- **The project record** supports level 3: it holds the pre-registration log and the output of the ordering check, whose counts are in §1.4. The check itself needs the working repository's history and cannot be rerun from the release. The record's files are restricted.

**The ordering check's counts.** `README.md` (level 3) says what the check does. Its output has 79 rows, one for each of the bundle's `owner__*.json` files and its two metadata files: PRECEDES a section of its own 58; PRECEDES amendment CT's opening heading only 7; SAME_COMMIT 1; UNDETERMINED 13.
- **PRECEDES a section of its own:** the file names one or more sections of the pre-registration log, and the latest of the commits that added those sections' headings comes before the commit the file records.
- **PRECEDES amendment CT's opening heading only:** the file names amendment CT, the log's last amendment, as a whole and no section of it. That amendment was declared section by section, so the verdict says the amendment had begun, not that the file's own section was declared first.
- **SAME_COMMIT:** of what the file names, the check reads an amendment as a whole and no section of it. The check compared the commit that the file records with the commit that adds that amendment's heading, and found them the same, so the history does not order the two. As with the files that name amendment CT as a whole, the verdict is about the amendment, not about the file's own section.
- **UNDETERMINED:** the file records no commit, and the check does not guess one.

The check itself gives one of four verdicts, and the classes above split the first: PRECEDES 65 (the first two classes), SAME_COMMIT 1, DOES_NOT_PRECEDE 0 (no file has it) and UNDETERMINED 13.

## 2. Coverage: at which level each reported number is recovered

`README.md` ("Reproducing the reported numbers") defines the levels and counts the rows at each. This section is the table itself. **The first two tables of §2.1 are keyed to the study's reported numbers, not to the workshop paper; the third, added on 2026-11-16, is keyed to the workshop paper.** This release accompanies the full study; the workshop paper gives a subset of the study's numbers, and §2.5 lists the parts it leaves out. An extended version of the paper is in preparation. The table was made on 2026-10-29 from a list of the numbers in the planned full write-up of the study, passage by passage, together with `scripts/reproduce_table1.py`, the checks that ran when the bundle was built, the bundle's manifest and the record's table of numbers. **The row labels, and the comments in the code that say "camera-ready" or cite an appendix or a table, refer to that write-up.** It was first planned as the camera-ready text, before the workshop paper was scoped to a subset of the study. It is not in this repository, and the workshop paper's own labels need not match. There is one row for each passage in that list and owning section of the table of numbers, split where one section's numbers sit at different levels; it is not one row per number. **Rows added on 2026-11-16.** That list held the numbers of text that was new or changed after the paper was submitted for review, so a result that stood unchanged had no row. §2.1's third table adds a row for every measured result that the final workshop paper prints, in digits or in words, and that the first two tables did not hold; the text above that table says what was searched and what counts as a measured result. **Where a number traces to.** Each row's owner column says where the record holds the number: a section of the record's table of numbers, a section of the pre-registration log, or a working document of the record. **The owner is where the record prints the number, and that can be a section which carries it from another analysis.** What the record says of a result's standing, that is, how the result stands to its declaration, is read in the section of the result's own analysis; the record's `README_RECORD.md` §5 says where the record states it.

How to read the columns:
- **edit** is the row's key: the label that the list gives the passage stating the number. Where the label begins with a number or a letter and `-app`, that is the section or appendix of the planned full write-up (`1.3` is in its Section 1, `K-app` in its Appendix K); labels that begin with `X` are main-text passages that were condensed, and carry no section; `B0` and `Table 2` are tables; `FN-A` is a footnote. The rest of a label numbers the passages and has no meaning outside this table. Labels that begin with `W` are the rows of §2.1's third table: `W`, the page of the workshop paper on which the passage stands, and a running number. **The other labels are this table's keys and are not references to the workshop paper,** whose own labels need not match and which leaves some passages out (§2.5): a reader finds a row by the numbers in its second column.
- **NoR owner** is the section of the record's table of numbers (`docs/NUMBERS_OF_RECORD.md`, in the project record) that carries the number. `PREREG §…` is a section of the pre-registration log, and `MP` is the record's methods-provenance document, `docs/METHODS_PROVENANCE.md`. That document and `docs/GOTCHAS.md`, whose numbered entries are the cases behind the project's working rules, are working documents of the record. "(as …)" gives the form in which the owner writes the same value: another rounding, a share for a per cent, or the numbers from which the value is read.
- **bundle file(s)** are names of files in the bundle. `sim_rule1_n19`, `sim_rule2_n19`, `sim_rule3_n19` and `sim_rule3_rawdot_n19` have `n_compare` = 19 (§1.2).
- **evidence** says what the level rests on:
  - `RT1:<name>` is a check in `scripts/reproduce_table1.py`, from its `RECORD` or `NINE_ARM` table.
  - `G[<file>]:"<what>"` is a check that ran when the bundle was built; the rows call these checks gates. `<file>` is the check's output, which is kept in the working repository and is not released. Every gate cited passed, with BIT_IDENTICAL or PASS.
  - `NoR Lnnnn` is the line of `docs/NUMBERS_OF_RECORD.md` that names the owner.
  - "entries" are entries of the record's corrections log.
  - A path such as `/full_fit/0.60/across_seed_mean_pp` is a field of the owner file the row names, followed by the value read there.
  - `recount (2026-11-16)` is a count made once, on that date, from the bundle's tables. The row gives the file, the column or columns and the condition, which is enough to make the count again. It is rerun neither by the build that made the release nor by `scripts/reproduce_table1.py`. A row whose recount was made by a check that ran when the bundle was built cites that check (`G[…]`) and not a date.
  - Every value read or recounted in this way was compared with the printed number at the printed precision, by a check that is kept in the working repository.

What "(design)" and "(derived)" mean:
- **(design)**: a seed count, `n_compare`, k, width or θ. It is a parameter the bundle files are organised by (seed labels, column labels, `meta.json`), not a value any check tests. Its level is given only where an owner file carries it.
- **(derived)**: an arithmetic combination (a difference or a share) of values that are themselves checked at the level shown.

Other terms the rows use:
- **q1, q3** after a section of the table of numbers: that section's first or third qualifier, a condition the record attaches to the number.
- **MISMATCH**: a stored result file that did not reproduce bit for bit when its producer was run again; such a file is not in the bundle.
- **exempt `/identity`**: a gate compares a recomputed result file with the stored one key by key. The `identity` block (paths, hashes, host, commit) differs by construction and is not compared.
- **`SINGLE_FETCH`**: a published figure taken from one fetch of its source's own text, by one reader on one date, with no second reading.
- **top-merged**: the labelled sensitivity fit that two arms have in place of a primary slope, with the top firing-rate bin merged.
- **`s_f`**: the record's threshold-independent summary of a feature's match similarity.
- **Table 1, Table 2, Tables I1 to I3, Table K1 and Figure I1**, where a row names them, are the tables and the figure of the planned full write-up. Not all of them are in the workshop paper.

#### Results the workshop paper prints that the tables above did not hold (added 2026-11-16)

The two tables above were made from the numbers in the text of the planned full write-up that was new or changed after the paper was submitted for review. A result that stood unchanged since submission had no row, and neither did a few numbers that entered the final text later. The table below adds a row for every measured result that the final workshop paper prints and that no row above holds: 61 rows. Every page of the paper was searched twice: for numbers in digits, and for results written as words, which are number words, fractions ("half", "three-quarters"), multiples ("ninefold", "doubles"), "none" and "neither", and statements over all of a set ("every", "each", "all", "both", "no", "any", "most", "never", "always"). A result that the paper states only in words is an item of the row of its passage, in the paper's words ("fourteen near-identical proteins"; "Forty of the 64 concept cells"; "this ordering holds at every detection threshold we can estimate"). Where the words restate or round a number that the paper prints in digits, or count or compare numbers that it prints in digits ("a ninefold range" beside the two ends of the range; "two are negative" of four estimates that a table prints), they have no item of their own: the row of those digits is their row.

**What counts as a measured result.** A measured result is a number that running the pipeline or an analysis on the data produced: a rate, a count, an estimate, an interval's edge, a percentile or another statistic of a measured distribution, a test statistic, or a number derived from those by arithmetic. A design or configuration value was fixed without reference to the outcome: a model or training setting, a threshold or its grid, a bin edge, a pre-declared bar or cut, an admission criterion, a number of draws, the size of an array, of a population an analysis is defined on or of a split of that population that it is run on, or a worked illustration. The size of a population is a design value when the data, the split and the configuration fix its members (the 51,943 scored proteins and their two halves; the 3,821 proteins with an experimental label and their 1,471,542 residue rows), and a measured result when its members depend on what the trained dictionaries did (the concepts detected and the cells counted over them: 650, 552, 109,044 and 92,462). The outcome of a pre-declared rule applied to measurements that depend on what the trained dictionaries did is a measured result (the six bins that the collapse rule retained, which the paper prints with their edges, and the 384 strata that follow from them; the edges of the grid that the rule starts from are design values). A criterion applied to the annotations alone, such as the one that admits a concept, fixes a population by the data and the configuration, and its size is a design value (the 712 concepts of the library and the 703 of the pool). A count made on the data that the paper states as a finding is a measured result, by the first sentence of this rule, also where the data, the split and the configuration fix what is counted. Whether the paper states a count as a finding was decided by reading its sentence, row by row; that is a judgement and not a rule. A grid value that only locates a result ("at θ = 0.30") is a design value. Where the content of a sentence is which grid values (between which thresholds a sign changes), that is a result stated by thresholds, and it has a row. The rows below hold measured results, with one exception: row W25.1 holds the sizes of the two halves of a split, which are design values by this rule, and is kept with its owner.

### 2.6. Terms used in the tables

Terms that the rows of §2.1, the lists of §2.5 or `GUIDE.md` use, each in a line or two:
- **`b_dec`**: a dictionary's decoder bias, a vector of the model's width that is subtracted from an activation before it is encoded and added back after it is decoded. **The `b_dec`-swap ceiling** (rows 4.6, 5.4 and 7.3) is the activation correlation that a feature reaches with itself when another seed's decoder bias is put in place of its own: about 0.99 and not 1, a pilot measurement.
- **F1.5** (row 4.6): the fifth of the numbered commitments of §F1 of the pre-registration log, that the mechanical ceiling of the match rate be measured in each firing-rate bin before the regression is run. The log cites it as F1.5 and has no heading of that name.
- **θ\***: a rate-matched threshold. It is the threshold at which a mean match rate equals a reference rate, and the reference rate is always a mean match rate under decoder cosine at the reference threshold. Which reference rate is meant differs by row:
  - row 4.6 (activation correlation on the main ensemble): the main ensemble's rate with the same comparison set;
  - row 4.4 (the other matching rules among the anchors): the main ensemble's rate among its anchors;
  - row 5.4 (the `k = 64` arm) has two. The threshold that the row prints as θ\* is matched to the main ensemble's rate among its anchors, as in row 4.4. The thresholds of the four matching rules within the arm, on which the row's last line rests, are matched to another rate: the arm's own rate under the first matching rule;
  - row K-app (the width arms): the rate of the arm retrained at the ensemble's width.

  The section of the table of numbers that each row names gives its reference rate.
- **the M1 file** (row 5.4): an `owner__rf_marginal_m1_*.json` file. M1 is the log's name for the measurement of the distribution of the match counts; its result file holds, among other things, the mean match rate at each threshold.
- **arm B, `T = 1`** (§2.5; rows A-app 2): the classification of features as annotation-aligned or orphan has two arms, by the null that a feature's alignment is tested against. Arm A's null shifts each protein's annotations circularly within the protein; arm B's permutes them across proteins of similar length, and arm B is the primary one. `T` is the least number of experimentally validated residues that a concept must have to enter the classification, and `T = 1` is its primary value.
- **the label store** (rows 6.9, 7.1, 7.4 and others): the file of residue-level labels built from the Swiss-Prot annotations, with the evidence code of each label. It is not released.
- **gather** (row W20.1): the step that passes the evaluation residues through a dictionary and collects, for each feature, the residues on which it fires.
- **the anchor's six rates** (row L-app): the six totals of the prediction ledger's opening tally, its entry `anchor`, taken after amendment AV. This anchor is the ledger's starting point and not an anchor dictionary.
- **the AP-arithmetic exemption** (row FN-A): a qualifier that the record attaches to the slope at `k = 64`. Its average precision was summed on CPU and its null on GPU, with both gathers on one class of GPU, where the record's rule asks that a statistic and its null be computed on one device class. The exemption allows that for this arm; its control put the record's own pair through the same path and reproduced it bit for bit.
- **`B0`, `Table 2`** (edit labels): tables of the planned full write-up of the study, which is not released (§2).
- **the stated-hash gate** (`GUIDE.md` §3): a check, made when the bundle was built, of the sha256 of each stored artifact that the build read against the hash that the record states for that file. `meta_ext.json` counts its verdicts (§3).
- **`G[<file>]`** (the evidence column): a gate, which is a check made when the bundle was built. The files that hold its output are not released, so a reader cannot open them. For each family of gates `meta_ext.json` holds how many there were and whether all passed (`families`: `n_gates`, `all_pass`): 294 gates in 12 families, all passed.

**JSON.** Only string literals are rewritten, so no number is re-serialised. The build then parses both versions with every number kept as its literal text, and requires the exported file to equal the original with the table applied to each string.

**The hash map.** Replacing a path inside a file changes the file's sha256. `release/export_hash_map.csv` has 84 rows, each with the original and the exported sha256 of one file:
- every bundle file the substitution changed (62 of 127, the bundle's manifest among them; 65 are byte-identical to the files the analyses wrote), the decoders' manifest, and the 10 decoder files, all of which changed;
- 1 evidence file of the project record that the substitution changed and whose original hash a document of the record states. An evidence file that is a byte-for-byte copy of a bundle file is released as the bundle's exported bytes;
- 10 configuration files. Stored artifacts record a configuration file's hash as `config_hash`, so no document is rewritten for them: the documents keep the original value, the map's last column says so, and the row only lets a reader resolve the exported file.

Other files the placeholders changed are not in the map.

**Which documents state which hash.**
- **The exported hashes:** the manifests and the prediction ledger in this repository, and the project record's table of numbers and corrections log. Hashes rewritten through the map, full and abbreviated: `docs/NUMBERS_OF_RECORD.md` 54; `docs/CORRECTIONS.md` 6; `docs/prediction_ledger.json` 5.
- **The original hashes, as they were when written:** the pre-registration log and the record's other documents, which are not rewritten. 62 files of the project record state one, in full or abbreviated (counted as a hex string of eight or more characters that begins the original sha256 of a file the documents were rewritten for); the map's first column resolves it. In this repository, `release/derived/meta_ext.json` states original hashes, those of the configuration files (below).
- **Inside the bundle,** the manifest states exported hashes, and so do the two `meta` files for the files the bundle ships. `meta_ext.json`'s rows for its inputs from the working repository (the configuration files, the log, the table of numbers) state the hashes those files had there. Only full 64-character hashes are mapped inside the bundle: 17 owner files also record the first 16 characters of the sha256 of an input they read, 22 times for a file the substitution changed, and those stay the original files' (the files as they were read).

**Notes inside the bundle that were written before the export.** The last column of the bundle's manifest and the entry `levels` of `meta_ext.json` were written when the bundle was built, and the export does not reword them. Two things in them are read with this paragraph. They call the owner files "verbatim" (77 rows of the manifest, and `levels`): the export replaced identifiers in 59 of the 77 owner files, and the other 18 are byte-identical to the files the analyses wrote. And where they give a coverage level that differs from the tables of §2, the tables hold: the manifest's 3 rows for the `subspace_*` files say RECOUNTED beside §20.22 and §20.25, whose figures are RE-READ (§2.4), and `levels` gives one level for each kind of evidence, not one for each number.

**The one UNRESOLVED verdict in `meta_ext.json`.** For each stored artifact among the inputs that the bundle's build read, `meta_ext.json` says whether the record states the file's sha256 (`inputs_recorded`, `record_hash_verdicts_artifact_inputs`): MATCH 96, NOT_STATED 484, UNRESOLVED 1. A file is counted once for each family of checks that read it: the 581 verdicts are of 262 files. The other inputs (files of the working repository or of the bundle, and paths of the interpreter and the system) have no verdict. UNRESOLVED means that a hash stands on the line of the record that names the file or within the two lines after it, that none of those hashes is the file's, and that the naming line does not itself state one hash alone, which would be a mismatch. The one such input is `rule_interior_mass_co.h5`, a file of the project's storage on the cluster that is in no part of the release. The record names it as the input of the comparison of the matching rules among the anchors and prints, two lines below the name, the sha256 of that job's result file, `ct20_rules_n19_ct.json`, which the bundle ships as an owner file. The record states no hash for the input itself (the log's §CT18-D4-R).

**Two searches of the result.** After the build, every file of the repository, the bundle and the project record is searched twice, by two programs written separately: the build's own scan, and a search written for a separate check of the release before publication, which reads each file's raw bytes, the contents of compressed files, decoded JSON, the cells of large tables, h5 attributes and string data, file names, and archive headers. Each first has to find identifiers planted for the other, in every kind of container. Both look for every value of the private table in any letter case, and for anything shaped like an account, an address, a key or a UUID that the table does not know. One hit in either fails the build; this build has none.

**Path placeholders in code:** `README.md`, level 1, says what a rerun of the pipeline must set, and `release/path_placeholders.tsv` lists the files. Checking the reported numbers against the bundle needs none of them.

## 5. Not done

- **The pipeline was not rerun from this export.** Level 1 of `README.md` was run in the working repository, on the cluster, over the months of the project; the exported code with its placeholders set was not run end to end.
- **The h5 inputs are not in the ordering check.** Its output covers the bundle's 79 owner and metadata files. The h5 files that `meta_ext.json` records as inputs were not added.
- **The checks of the bundle's build that read artifacts outside the bundle were not rerun on the exported bundle.** They compare bundle files with artifacts that are not released. Not rerunning them is safe because of what the substitution changed, 62 of the bundle's 127 files:
  - 61 JSON files. Each must equal its original with the table applied to its strings, every number compared as its literal text, or the build stops. Where a file states another bundle file's full sha256, that hash is then mapped.
  - The manifest, whose every row is checked against the exported file it names.
  - Nothing else: the build stops if the substitution changes a bundle file of any other kind.

  So every value those checks read is unchanged, and the checks that read only the bundle were rerun (§4).
- **One citation in the code does not resolve, and it was not corrected.** A comment in each of `src/analysis/artifact_identity.py` and `src/analysis/preflight.py` cites "gotcha 2b" beside amendment O. A "gotcha n" in the source is rule n of the project's numbered working rules, whose cases are in the project record, and the record's files are restricted (`README.md`, "What is released"). Rule 2 there has no part (b), so the rule the two comments mean is not established. The comments are left as written: they were not corrected in this release. No code depends on them.
- **The comments in the code were not reworded for a reader who does not have the record.** They cite the working repository's operating manual, its numbered rules and the sections of the pre-registration log, as written (`README.md`, "Citations in the code"; `GUIDE.md` §3). They were not reworded in this release.
- **The extended version of the paper is not cited yet.** The paper is cited under the workshop paper's title; `CITATION.cff` and `README.md` ("Paper") say so. The extended version's title may differ, and its citation will come with it.
